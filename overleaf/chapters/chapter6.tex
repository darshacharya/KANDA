\section{Languages, Tools, and Platforms}
\label{sec:lang_platform}

\subsection{Embodiment layer}

Firmware targets the ESP32 using the Arduino framework with Espressif's Arduino core (v3 or newer) so that PWM, GPIO, and I\textsuperscript{2}C APIs match classroom and hobbyist practice while retaining access to the native peripherals~\cite{espressif2023esp32}. The sketch \textit{phase2\_obstacle\_avoidance.ino} is edited and flashed with the Arduino IDE or PlatformIO. Libraries used in the shipped configuration include \textit{Wire}, \textit{Adafruit\_SSD1306}, \textit{Adafruit\_GFX}, and \textit{ArduinoJson} for OLED and inbound JSON parsing.

\subsection{Intelligence layer}

The companion computer runs Linux (Raspberry Pi OS or equivalent) with Python~3.10+. Dependencies are minimal by design: \textit{requests} for HTTP (Groq and NVIDIA NIM use OpenAI-compatible APIs), \textit{pyserial} for UART, \textit{openwakeword} for offline wake detection, and \textit{picamera2} for camera access. No separate web stack or database is required for the baseline closed-loop demo; configuration is read from environment variables and the central \textit{config.py} module. \textbf{Table~\ref{tab:impl_stack}} summarises the technology choices.

\section{Repository and Module Layout}
\label{sec:repo}

The project groups firmware and intelligence code under a single repository root:

\begin{itemize}[nosep]
  \item \textit{firmware/}: Arduino C++ sketch for ESP32 (obstacle avoidance, command execution, telemetry)
  \item \textit{vision\_module/}: \textit{main.py} orchestrator, \textit{config.py} settings, \textit{task\_agent.py} reasoning and vision, \textit{camera.py}, \textit{vlm.py}, \textit{voice\_command.py}, \textit{wake\_word.py}, \textit{telegram\_input.py}, \textit{speaker.py}
  \item \textit{docs/}: pin and power notes for reproducible wiring
\end{itemize}

The intelligence layer follows a modular design: the orchestrator (\textit{main.py}) imports task agents and I/O modules; \textit{task\_agent} dispatches to Groq (text) or NVIDIA NIM (vision) as needed. Setup on a fresh Pi: install dependencies from \textit{requirements.txt}, export \textit{GROQ\_API\_KEY} and \textit{NVIDIA\_API\_KEY}.

\section{Serial Protocol and Message Formats}
\label{sec:protocol}

Telemetry (ESP32 $\rightarrow$ Pi). Each cycle the firmware prints one ASCII line:
\textit{F:<cm> L:<cm> R:<cm> -> <LABEL>}, where distances are in centimetres and \textit{<LABEL>} mirrors the current motion decision string for operator traceability. The Pi's \textit{read\_telemetry()} splits on \textit{->}, tokenises \textit{F:}, \textit{L:}, and \textit{R:}, and returns a dictionary of floats plus the trailing action string.

Commands (Pi $\rightarrow$ ESP32). Valid lines are a single JSON object per line, UTF-8 encoded, terminated by \textit{\textbackslash n}. The firmware uses \textit{deserializeJson} into a small static document, reads \textit{action} and \textit{speed}, clamps speed to $[0,255]$, and dispatches to motor primitives.

This contract keeps the wire format debuggable in a serial console while remaining strict enough for deterministic parsing on both sides~\cite{vemprala2024chatgpt}.

\section{Firmware Implementation Highlights}
\label{sec:impl_fw}

Ultrasonic ranging uses a standard trigger pulse and \textit{pulseIn} on echo pins; input-only GPIO (e.g.\ 34, 35) are used for echoes with resistor dividers documented in hardware notes. Motor direction uses paired digital outputs per half-bridge; speed uses LEDC PWM at 1\,kHz with 8-bit duty resolution on the core v3 API (\textit{ledcAttach}).

AI execution. Function \textit{executeAiCommand} parses JSON, applies \textit{constrain} on speed, and maps seven string actions to \textit{forward}, \textit{backward}, pivots, \textit{slightLeft}/\textit{slightRight} (asymmetric PWM while holding forward direction bits), or full stop.

Mode logic. Successful JSON reception switches to \textit{AI\_MODE} and refreshes a millis timer; exceeding \textit{AI\_TIMEOUT\_MS} without a new line returns control to rule-based \textit{AUTO\_MODE} so the vehicle retains basic safety without the Pi~\cite{brooks1986robust}.

\begin{lstlisting}[language=C++, basicstyle=\itshape\footnotesize, caption={Excerpt: JSON command dispatch on ESP32 (simplified)}, label={lst:fw_json}]
bool executeAiCommand(const String& jsonLine) {
  StaticJsonDocument<128> doc;
  if (deserializeJson(doc, jsonLine)) return false;
  const char* action = doc["action"] | "stop";
  int spd = doc["speed"] | speedVal;
  spd = constrain(spd, 0, 255);
  setSpeed(spd);
  if      (!strcmp(action, "forward"))       forward();
  else if (!strcmp(action, "slight_left"))   slightLeft();
  else if (!strcmp(action, "slight_right"))  slightRight();
  else if (!strcmp(action, "stop"))          stopMotors();
  // ... remaining actions ...
  return true;
}
\end{lstlisting}

\section{Intelligence Layer Implementation}
\label{sec:impl_ai}

\subsection{Configuration}

\textit{config.py} reads \textit{KANDA\_SERIAL\_PORT}, \textit{GROQ\_API\_KEY}, and \textit{NVIDIA\_API\_KEY}, and defines \textit{VALID\_ACTIONS}, \textit{LOOP\_INTERVAL\_SEC}, \textit{LLM\_TIMEOUT\_SEC}, and speed bounds. Centralising limits ensures the validator and prompt stay aligned~\cite{huang2023grounded}.

\subsection{Prompting and inference}

\textit{context\_builder.py} prepends a fixed hardware-and-safety brief (valid verbs, speed range, distance heuristics) and appends live front/left/right readings. \textit{llm\_client.py} configures the Groq and NVIDIA NIM clients (OpenAI-compatible API), calls inference with temperature~0.1 and \textit{max\_tokens}=256, then strips optional markdown fences and extracts the first JSON object with a regular expression before \textit{json.loads}~\cite{ahn2022saycan}.

\subsection{Validation and actuation}

\textit{safety\_validator.validate} never raises: it returns either the cleaned command or a stop dictionary. The orchestrator then calls \textit{UARTBridge.send\_command}. Listing~\ref{lst:val_py} shows the clamping behaviour for out-of-range speed.

\begin{lstlisting}[language=Python, caption={Speed coercion and clamping in the validator}, label={lst:val_py}]
def validate(cmd: Any) -> dict:
    if not isinstance(cmd, dict):
        return {"action": "stop", "speed": 0}
    action = cmd.get("action")
    speed = cmd.get("speed", config.DEFAULT_SPEED)
    if not isinstance(action, str) or action not in config.VALID_ACTIONS:
        return {"action": "stop", "speed": 0}
    try:
        speed = int(speed)
    except (TypeError, ValueError):
        return {"action": "stop", "speed": 0}
    speed = max(config.SPEED_MIN, min(config.SPEED_MAX, speed))
    return {"action": action, "speed": speed}
\end{lstlisting}

\subsection{Orchestrator loop}

\textit{main.py} opens the serial port, applies a short post-open delay for MCU reset, registers signal handlers that send \textit{stop} on SIGINT/SIGTERM, and loops: read telemetry, short-circuit to stop if parse fails, dispatch to task agent, validate output, transmit, sleep for \textit{LOOP\_INTERVAL\_SEC}. The task agent decides whether to call Groq (for text reasoning) or NVIDIA NIM (for vision). Exceptions per cycle trigger stop but keep the process alive for the next iteration.

\subsection{Body-Context Assembly}

\textbf{Figure~\ref{fig:bodyctx_ch6}} shows how the body-context block is assembled from multiple sources before each Groq or NVIDIA NIM call. Five distinct data sources contribute to the final prompt: the static hardware description (valid actions, speed range, physical constraints), live ultrasonic readings with proximity warnings, the most recent scene description from the vision model, the last few executed actions for temporal context, and optional user speech or image input for multimodal queries. This assembled block is prepended to every inference request so that the language model always reasons about the robot's current physical situation rather than a generic scenario. \section{Difficulties Encountered and Mitigations}
\label{sec:difficulties}

\begin{description}[style=nextline]
  \item[Serial bring-up] USB-UART adapters versus GPIO UART on the Pi require different device nodes; exposing \textit{KANDA\_SERIAL\_PORT} avoids hard-coding paths.

  \item[ESP32 reset on open] A fixed delay after \textit{Serial} open on the Pi lets the bootloader finish before the first command.

  \item[Non-JSON or fenced LLM output] Regex-based JSON extraction and low temperature reduce parse failures; the validator maps all failures to stop~\cite{huang2023grounded}.

  \item[Stochastic latency] Cloud round-trip time exceeds the ultrasonic control period; the architecture treats LLM planning as a slow outer loop while firmware enforces local timeouts and AUTO\_MODE fallback.

  \item[5\,V sensor echoes] HC-SR04 echo lines are level-shifted before ESP32 inputs to avoid violating 3.3\,V tolerance.

  \item[API credentials] Keys are supplied only via environment variables to keep secrets out of version control.
\end{description}

\section{Build and Run Procedure}
\label{sec:run}

Firmware: Select the ESP32 board profile, set the correct USB port, compile, and upload \textit{phase2\_obstacle\_avoidance.ino}. Confirm OLED initialisation and serial banner at 115200 baud.

Pi: Install Python dependencies (\textit{pip install -r requirements.txt}), export \textit{GROQ\_API\_KEY} and \textit{NVIDIA\_API\_KEY}, optionally \textit{KANDA\_SERIAL\_PORT}, then run \textit{python3 main.py} from \textit{vision\_module/}. Verify telemetry lines in the log before trusting motion.

\section{Summary}
\label{sec:ch6summary}

This chapter recorded the concrete implementation of KANDA: Arduino C++ firmware with JSON actuation and dual-mode policy, Python modules for UART, hardware-aware prompting, task agent dispatching to Groq (text) and NVIDIA NIM (vision), and mandatory validation, plus the newline-delimited serial contract linking the two runtimes. Configuration and failure handling prioritise safe stop behaviour over aggressive motion. Standalone test blocks at the bottom of utility modules, plus serial console traces, served as informal regression checks during integration; Chapter~\ref{ch:testing} formalises the test strategy and requirement mapping.
