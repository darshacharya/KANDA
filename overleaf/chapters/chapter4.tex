\chapter{High Level Design}
\label{ch:hld}

This chapter presents the high-level design of \textbf{Knowledge-driven Autonomous Navigation and Decision-making Agent (KANDA)}. It records design considerations that follow from the Software Requirement Specification (Chapter~3), the phased development approach, architectural strategies for the dual-processor stack, an overview diagram of the layered architecture, and data flow diagrams at three levels of abstraction. The design separates real-time embodiment on the ESP32 from asynchronous language-model inference on the Raspberry Pi, with an explicit validation boundary before actuation~\cite{brooks1986robust,huang2023grounded}.

%-------------------------------------------------------------------
\section{Design Considerations}
\label{sec:design}

%-------------------------------------------------------------------
\subsection{General Considerations}
\label{subsec:general}

The following considerations shaped the high-level design of KANDA:

\textbf{Safety before motion:} Large language model outputs are stochastic; direct execution on hardware would risk invalid verbs, out-of-range speeds, or malformed structures~\cite{ahn2022saycan}. Every candidate command therefore passes through schema checks, membership in a finite action set, and numeric clamping before PWM or direction pins change~\cite{huang2023grounded}.

\textbf{Layered embodied architecture:} Sense--reason--act behaviour is organised into layers---physical sensing and actuation, microcontroller execution, serial messaging, and companion-computer reasoning---consistent with layered control for mobile robots~\cite{brooks1986robust}. Each layer exposes narrow interfaces (telemetry lines, JSON lines) so responsibilities remain traceable.

\textbf{Timing separation:} Ultrasonic sampling and motor PWM require deterministic loops on the ESP32; inference over HTTPS to Gemini is asynchronous and variable in latency~\cite{vemprala2024chatgpt}. The architecture never assumes sub-second LLM latency for safety-critical reactions; firmware timeouts and AUTO\_MODE fallback preserve basic collision avoidance when the intelligence layer is slow or unavailable.

\textbf{Structured command interface:} Motor intents are expressed only as single-line JSON objects with \texttt{action} and \texttt{speed}, aligning language-model outputs with executable motor primitives~\cite{vemprala2024chatgpt}. Natural language never crosses the UART boundary to firmware parsers.

\textbf{Observability:} The intelligence layer logs cycles, telemetry summaries, raw model output (where enabled), validation outcomes, and errors on the Raspberry Pi. The OLED on the robot surfaces mode and behaviour for the operator.

\textbf{Graceful degradation:} Loss of cloud connectivity or Python process failure must not leave motion undefined: firmware reverts to rule-based obstacle avoidance after a UART silence threshold while electrical limits remain enforced.

%-------------------------------------------------------------------
\subsection{Development Methods}
\label{subsec:dev_methods}

KANDA was developed using an \textbf{incremental phased methodology}: each phase delivers a working baseline before the next layer is added.

\begin{description}[nosep]
  \item[Phase 1, Foundations:] Problem formulation, literature survey, requirements and architecture sketches (Chapters~1--3).
  \item[Phase 2, Embodiment layer:] ESP32 firmware with HC-SR04 sensing, TB6612FNG motor drive, SSD1306 display, voltage-divided ECHO inputs, and standalone obstacle-avoidance logic (AUTO\_MODE baseline).
  \item[Phase 3, Intelligence layer:] Raspberry Pi hosts Python modules for UART I/O, hardware-aware prompt construction, Gemini API calls (default \textbf{Gemini 2.5 Flash}), JSON validation, and closed-loop command transmission; firmware extended for AI\_MODE with watchdog fallback.
  \item[Phase 4 (future), Multimodal agent:] Camera, microphone, speaker, and richer planners---out of scope for the current high-level design baseline but anticipated using composed multimodal reasoning~\cite{zeng2023socratic,wu2023tidybot}.
\end{description}

\section{Architectural Strategies}
\label{sec:arch_strat}

%-------------------------------------------------------------------
\subsection{Programming Language and Runtime Selection}
\label{subsec:lang}

\textbf{Arduino-compatible C++} targets the ESP32 firmware: direct register and peripheral access, deterministic sampling intervals, mature motor-control patterns, and small binary size~\cite{espressif2023esp32}.

\textbf{Python~3} targets the Raspberry Pi intelligence layer: the official Google Generative AI client (\texttt{google.generativeai}), \texttt{pyserial} for UART, rapid iteration on prompts and validation rules, and structured logging~\cite{vemprala2024chatgpt}.

\textbf{JSON line protocol} over UART at 115,200 baud provides human-readable debugging, explicit message boundaries (newline-terminated lines), and straightforward parsing on both ends without custom framing beyond newline delimiters.

%-------------------------------------------------------------------
\subsection{Future Extensions}
\label{subsec:future}

Planned extensions beyond the current baseline include multimodal prompts (vision and speech), longer-horizon planning~\cite{wake2023gptrobot}, on-device buffering of telemetry for offline analysis, and optional local-model experiments---without removing the validation layer before actuation~\cite{huang2023grounded}.

Fig.~\ref{fig:sysarch} shows how responsibilities are split. The \textit{intelligence layer} performs hardware-aware prompting, calls the Gemini API (default Gemini~2.5 Flash), validates JSON commands, and transmits safe motor intents over UART. The \textit{UART link} carries newline-terminated ASCII lines in both directions. The \textit{embodiment layer} parses commands, drives motors, samples ultrasonic sensors, refreshes the OLED, and enforces mode logic including fallback to AUTO\_MODE. The \textit{physical plant} captures sensors, actuators, and power paths documented in hardware chapters.

\section{Summary}
\label{sec:ch4summary}

This chapter presented the high-level design of KANDA. Design considerations emphasised validation before actuation~\cite{huang2023grounded}, affordance-grounded command formats~\cite{ahn2022saycan}, layered embodied structure~\cite{brooks1986robust}, and resilience to stochastic cloud latency~\cite{vemprala2024chatgpt}. Development followed phased delivery from embodiment to intelligence, with a documented path toward multimodal extensions~\cite{zeng2023socratic,wu2023tidybot}.

Architectural strategies justified C++ on the ESP32 and Python on the Raspberry Pi, linked by a newline-delimited JSON and telemetry UART protocol~\cite{espressif2023esp32}. Figure~\ref{fig:sysarch} summarised the intelligence, UART, embodiment, and physical tiers. Data flow diagrams at Level~0 (\ref{fig:dfd0}), Level~1 (\ref{fig:dfd1}), and Level~2 (\ref{fig:dfd2a}, \ref{fig:dfd2b}) traced information from sensors and cloud inference to motor outputs. Chapter~5 refines these sub-systems into detailed module-level design aligned with the implementation directories.
