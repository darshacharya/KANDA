\chapter{Software Requirement Specification}
\label{ch:srs}

This chapter presents the Software Requirement Specification (SRS) for \textbf{Knowledge-driven Autonomous Navigation and Decision-making Agent (KANDA)}. It describes the product perspective, functions, user classes, constraints, and specific functional and non-functional requirements for the dual-layer system (ESP32 embodiment layer and Raspberry Pi intelligence layer). The SRS serves as the formal contract between the system design and the implementation. Design principles for grounding LLM outputs in robot capabilities follow established robotics--LLM practice~\cite{vemprala2024chatgpt,ahn2022saycan}.

%-------------------------------------------------------------------
\section{Overall Description}
\label{sec:overall}

%-------------------------------------------------------------------
\subsection{Product Perspective}
\label{subsec:perspective}

KANDA is a standalone embedded robotic system consisting of two cooperating software stacks:

\begin{itemize}[nosep]
  \item \textbf{Embodiment firmware (ESP32):} Arduino-compatible C++ firmware under \path|firmware/phase2_obstacle_avoidance/| on an ESP32 DevKit. It performs ultrasonic sensing, motor PWM control via TB6612FNG, SSD1306 OLED display updates, and UART messaging with the companion computer.

  \item \textbf{Intelligence layer (Raspberry Pi):} Python modules in \path|ai_layer/| that read telemetry from the serial port, compose a hardware-aware prompt, call the Google Gemini API, validate the returned JSON command, and transmit it to the ESP32.

\end{itemize}

The system interfaces with the following external components:

\begin{itemize}[nosep]
  \item \textbf{Gemini API:} Cloud-hosted Google \textbf{Gemini 2.5 Flash} (default model identifier \texttt{gemini-2.5-flash}) accessed via \texttt{google.generativeai}; requires \texttt{GEMINI\_API\_KEY} in the environment and network connectivity on the Raspberry Pi. The model id may be overridden with environment variable \texttt{GEMINI\_MODEL} for reproducibility and A/B testing~\cite{vemprala2024chatgpt}.

  \item \textbf{UART link:} Serial connection between Raspberry Pi and ESP32 at 115,200 baud. The device path is set via \texttt{KANDA\_SERIAL\_PORT} (for example \path|/dev/ttyS0| or \path|/dev/ttyUSB0|).

  \item \textbf{Power subsystems:} Battery, BMS, buck converter, and motor supply paths as documented in project hardware notes; software assumes stable power within component ratings.
\end{itemize}

KANDA is not a hosted web service in the deployed configuration; the Pi runs the AI layer as a local process (e.g.\ \texttt{python3 main.py}). The architecture separates real-time control on the microcontroller from asynchronous LLM inference on the companion computer, consistent with layered embodied systems~\cite{brooks1986robust,driess2023palme}.

%-------------------------------------------------------------------
\subsection{LLM Model Selection and System Alignment}
\label{subsec:alignment}

\textbf{Default model.} The intelligence layer targets \textbf{Gemini 2.5 Flash} (\texttt{gemini-2.5-flash}) as the default production model: it balances multimodal reasoning quality with latency and cost suitable for repeated calls in a physical control loop.

\textbf{Alignment (three layers).} ``Alignment'' here means keeping model behaviour consistent with safe robot operation, not merely stylistic compliance:

\begin{enumerate}[label=\arabic*., nosep]
  \item \textbf{Specification alignment (prompt):} The hardware-description prompt fixes the action grammar, speed bounds, sensor semantics, and explicit safety rules so the policy implied by the prompt matches platform affordances~\cite{ahn2022saycan,vemprala2024chatgpt}.
  \item \textbf{Decoding alignment (generation):} Low sampling temperature and JSON-only output contracts reduce gratuitous variance and ease parsing on the microcontroller path.
  \item \textbf{Runtime alignment (validation):} Every decoded command passes through the validator, which enforces a finite action set and numeric clamps before GPIO/PWM actuation---mirroring command-level grounded filtering~\cite{huang2023grounded}.
\end{enumerate}

Together these layers ensure traceability from sensor context $\rightarrow$ model proposal $\rightarrow$ validated actuator command.

%-------------------------------------------------------------------
\subsection{Product Functions}
\label{subsec:functions}

The primary functions of KANDA are:

\textbf{F1, Proximity sensing:} Sample three HC-SR04 ultrasonic sensors (front, left, right) each control cycle and compute distances in centimetres.

\textbf{F2, Telemetry transmission:} Format sensor readings as a single ASCII telemetry line and transmit from ESP32 to Raspberry Pi over UART for use in LLM context construction.

\textbf{F3, Prompt construction:} Build a hardware-description prompt including valid motion primitives, speed bounds, safety rules, and current sensor readings~\cite{ahn2022saycan}.

\textbf{F4, LLM inference:} Send the prompt to Gemini 2.5 Flash with low temperature and short maximum output length to obtain a JSON object with \texttt{action} and \texttt{speed} fields (one object per response).

\textbf{F5, Command validation:} Verify action membership in the configured whitelist, coerce speed to integer, clamp to $[0,255]$, and substitute a safe stop command on failure~\cite{huang2023grounded}.

\textbf{F6, Command transmission:} Serialize the validated command as one JSON line over UART to the ESP32.

\textbf{F7, Motor actuation:} Parse JSON on the ESP32 and drive TB6612FNG inputs (direction + PWM) to realise forward, backward, turns, slight corrections, or stop.

\textbf{F8, Status display:} Render current mode and behaviour on the SSD1306 OLED.

\textbf{F9, Dual-mode operation:} Switch to AI\_MODE when valid JSON lines are received from the Pi; revert to AUTO\_MODE (rule-based obstacle avoidance) after a configurable UART silence timeout (default 5000\,ms in firmware).

\textbf{F10, Safe shutdown:} On AI layer exit or error, send stop commands where applicable to leave the robot in a safe state.

\subsection{Constraints}
\label{subsec:constraints}

\begin{description}[style=nextline]
  \item[C1, Environment] Indoor, flat-floor operation assumed for specification and testing; outdoor use is outside the baseline SRS.

  \item[C2, Language] LLM prompts and documentation are English; future speech modalities are out of scope for this SRS revision.

  \item[C3, Network] Gemini inference requires outbound HTTPS from the Raspberry Pi; autonomous obstacle avoidance remains available without the cloud when operating in AUTO\_MODE on the ESP32 alone.

  \item[C4, Credentials] The Gemini API key must be supplied via environment variable; no hard-coded secrets in source repositories.

  \item[C5, Electrical] HC-SR04 ECHO outputs are 5V; ESP32 GPIO inputs require compliant level shifting (e.g.\ resistor dividers) as implemented in hardware.

  \item[C6, Real-Time Bound] LLM latency is non-deterministic; the system shall not assume sub-second planning latency while still maintaining safe motion limits via firmware timeouts and validation~\cite{huang2023grounded}.
\end{description}

\subsection{Design Constraints}
\label{subsec:design_constraints}

\begin{description}[style=nextline]
  \item[DC-01, Structured Commands Only] The intelligence layer shall issue motor intents exclusively as single-line JSON objects with \texttt{action} and \texttt{speed}. Free-form natural language shall not be sent directly to motor routines~\cite{vemprala2024chatgpt}.

  \item[DC-02, Validation Before Motion] No LLM output shall reach GPIO/PWM without passing through the validator aligned with affordance-grounding practice~\cite{ahn2022saycan,huang2023grounded}.

  \item[DC-03, Bounded Action Space] The legal action set shall remain finite and enumerated in both firmware expectations and Python configuration to prevent undefined behaviours.

  \item[DC-04, Graceful Degradation] Loss of cloud connectivity or Pi process failure shall not imply undefined motion: firmware falls back to AUTO\_MODE and avoidance thresholds.

  \item[DC-05, Observability] Serial logging on the Pi shall record cycles, errors, and safe-stop events sufficient for debugging demonstration and safety review.

  \item[DC-06, Configurability Without Reflash (Pi)] Serial baud, model name, loop interval, and timeouts shall be adjustable via configuration or environment where feasible without rebuilding firmware.
\end{description}

\section{Summary}
\label{sec:ch3summary}

This chapter presented the Software Requirement Specification for KANDA. The product perspective separated the ESP32 embodiment layer from the Raspberry Pi intelligence layer and identified external dependencies (Gemini 2.5 Flash API, UART, power). Section~\ref{subsec:alignment} formalised default model selection (\texttt{gemini-2.5-flash}) and a three-layer \textit{alignment} strategy: specification (prompt), decoding (temperature and JSON contract), and runtime validation before actuation. Ten product functions covered sensing, telemetry, prompting, inference, validation, actuation, display, dual-mode operation, and shutdown behaviour. Four user classes were defined from operator to maintainer. Constraints addressed environment, language, network, credentials, electrical interfacing, and stochastic LLM latency. Fifteen functional requirements, seven performance targets aligned with implementation constants, software and hardware dependency tables, and six design constraints formalised the contract for subsequent design chapters. Grounding and validation requirements~\cite{ahn2022saycan,huang2023grounded,vemprala2024chatgpt} are central to DC-01 and DC-02 and underpin the high-level architecture in Chapter~4.
