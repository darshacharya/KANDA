\chapter{Software Testing}
\label{ch:testing}

This chapter describes how \textbf{Knowledge-driven Autonomous Navigation and Decision-making Agent (KANDA)} was verified against the requirements in Chapter~\ref{ch:srs} and the designs in Chapters~\ref{ch:hld} and~\ref{ch:detail}. Testing is organised into \emph{unit} checks of pure-Python logic, \emph{integration} checks of the UART protocol between Raspberry Pi and ESP32, and \emph{system} exercises of closed-loop behaviour including firmware mode switching and cloud inference. Where hardware or API access was unavailable, procedures state the substitute (e.g.\ recorded serial traces or dry-run validators).

%-------------------------------------------------------------------
\section{Test Strategy and Environment}
\label{sec:test_strategy}

\textbf{Objectives.} Confirm that (1)~telemetry parsing and command serialisation are deterministic; (2)~the safety validator never emits out-of-vocabulary actions or speeds outside $[0,255]$; (3)~the ESP32 accepts one JSON line per message and maps actions to motor primitives; (4)~loss of telemetry, parse errors, or API faults result in a safe stop; (5)~firmware falls back from AI\_MODE to AUTO\_MODE after UART silence~\cite{huang2023grounded}.

\textbf{Environment.} Unit tests run on any host with Python~3.10+ using the modules under \texttt{ai\_layer/}. Integration and system tests use the physical stack (ESP32, TB6612FNG, sensors, OLED, Pi) on a clear bench, USB or GPIO UART at 115200 baud, outbound HTTPS for Gemini, and keys supplied via environment variables. Tests are identified as UT-$n$ (unit), IT-$n$ (integration), and ST-$n$ (system).

\section{Unit Testing}
\label{sec:unit_testing}

Unit tests exercise logic without powering motors: the validator script and telemetry parser accept synthetic inputs.

\subsection[Validator module]{Test suite: safety validator (\texttt{safety\_validator.py})}
\label{subsec:ut_validator}

The bottom of \texttt{safety\_validator.py} defines a standalone \texttt{main} block with labelled cases (valid forward, speed clamp high/low, invalid action, wrong type, empty dict). Running \texttt{python3 safety\_validator.py} prints input and normalised output for visual inspection.

\textbf{Field} & \textbf{Description} \\
\midrule
Test ID & UT-01 \\
Objective & Invalid or malformed commands map to a safe stop; in-range speeds pass; out-of-range speeds clamp. \\

\section{Summary}
\label{sec:ch7summary}

This chapter defined a three-level test strategy for KANDA: unit checks on the validator and telemetry parser, integration checks on the UART link, and system checks for AUTO\_MODE, AI\_MODE, timeout fallback, and safe degradation. Tabulated procedures support repeatability during demonstration and viva. Limitations include dependence on manual observation for motion quality and on network availability for Gemini-backed ST-02; future work may add scripted hardware-in-the-loop logging and timestamped test reports.
