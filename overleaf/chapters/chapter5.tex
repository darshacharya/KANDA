\chapter{DETAILED DESIGN}
\label{ch:detail}

This chapter gets into the details of how KANDA actually works, piece by piece. I explain what each software module does, how they talk to each other, and what happens in a typical control cycle from sensor to motor. I also show what happens when things go wrong. This chapter is where the rubber meets the road; this is what I actually implemented and why each piece is necessary.


%-------------------------------------------------------------------
\section{High-Level Design Overview}
\label{sec:hld_overview}

The deployment comprises a Raspberry Pi running the Python package tree \textit{vision\_module/}, an ESP32 running Arduino-compatible firmware, a duplex UART link at 115,200 baud, and HTTPS access to two cloud services: Groq (text reasoning and ASR) and NVIDIA NIM (visual understanding). \textbf{Figure~\ref{fig:hld_overview}} summarises the principal deployable blocks.

\begin{figure}[H]
\centering
\includegraphics[width=1.0\textwidth]{5_1.png}
\caption[High-level deployable blocks of KANDA]{\textbf{High-level deployable blocks of KANDA.}}
\label{fig:hld_overview}
\end{figure}

\textbf{Fig.~\ref{fig:hld_overview}} shows how the operator interacts with the intelligence layer on the Pi, how the Pi exchanges newline-terminated JSON and telemetry with the ESP32 over UART, how the ESP32 connects to the physical stack, and how the Pi dispatches to Groq (for text reasoning) and NVIDIA NIM (for visual understanding) over HTTPS.

\subsection[Configuration module]{Configuration module (\textit{config.py})}
\label{subsec:config}

Responsibility: Centralise tunable parameters and environment-backed secrets so other modules avoid scattering literals.

Key items: \textit{SERIAL\_PORT} (default \textit{/dev/ttyS0}), \textit{BAUD\_RATE} (115200), \textit{GROQ\_API\_KEY} and \textit{NVIDIA\_API\_KEY} from environment, \textit{VALID\_ACTIONS} as a Python set of seven string verbs, \textit{SPEED\_MIN}/\textit{SPEED\_MAX} (0--255), \textit{LOOP\_INTERVAL\_SEC}, \textit{LLM\_TIMEOUT\_SEC}, and \textit{DEFAULT\_SPEED} when the model omits speed.

%-------------------------------------------------------------------
\subsection[UART bridge module]{UART bridge module (\textit{uart\_bridge.py})}
\label{subsec:uart}

Responsibility: Encapsulate pyserial lifecycle and the ASCII protocols agreed with firmware.

Interface: Class \textit{UARTBridge} exposes \textit{connect()}, \textit{disconnect()}, context-manager support, and \textit{read\_telemetry()}. The send method serialises a one-line JSON object. The read method blocks up to \textit{SERIAL\_TIMEOUT}, decodes UTF-8, and parses telemetry lines into a dictionary.


Notes: A short sleep after opening the port accommodates ESP32 reset behaviour.

%-------------------------------------------------------------------
\subsection[Context builder module]{Context builder module (\textit{context\_builder.py})}
\label{subsec:ctx}

Responsibility: Concatenate a static hardware-and-policy preamble with formatted front/left/right readings so the LLM receives explicit affordances and safety hints on every call~\cite{ahn2022saycan}.

Interface: \textit{build\_prompt(telemetry, user\_speech=None, image\_b64=None)} returns one prompt string. Optional speech and image parameters are reserved for Phase~4 multimodal extensions; the LLM client already accepts \textit{image\_b64} for future attachment.

%-------------------------------------------------------------------
\subsection[LLM client module]{LLM client module (\textit{llm\_client.py})}
\label{subsec:llm}

Responsibility: Initialise the Groq and NVIDIA NIM clients (OpenAI-compatible API) once per process, invoke inference with low temperature (0.1) and short \textit{max\_tokens} (256), and recover a JSON object from arbitrary response text.

Parsing strategy: Prefer fenced markdown JSON if present; otherwise extract the first balanced brace segment and pass it to \textit{json.loads}. Failures surface as \textit{ValueError} for the orchestrator to translate into safe stop.

%-------------------------------------------------------------------
\subsection[Safety validator module]{Safety validator module (\textit{safety\_validator.py})}
\label{subsec:val}

Responsibility: Guarantee that only whitelisted actions and bounded speeds reach \textit{send\_command}; never raise, always return a usable dictionary~\cite{huang2023grounded}.

Rules: Reject non-dicts and unknown actions with fallback \textit{action}\,=\,\textit{stop} and \textit{speed}\,=\,0; coerce \textit{speed} with \textit{int()}; clamp to $[0,255]$ with logging when out of range.

%-------------------------------------------------------------------
\subsection[Orchestrator]{Orchestrator (\textit{main.py})}
\label{subsec:main}

Responsibility: Own the process lifecycle: configure logging, register SIGINT/SIGTERM handlers that send stop, open UART, loop with \textit{time.sleep(LOOP\_INTERVAL\_SEC)}, catch unexpected exceptions per cycle and issue stop, and disconnect cleanly.

Cycle ordering: Matches \textbf{Fig.~\ref{fig:activity_cycle}}: read telemetry; if missing, stop and skip LLM; else build prompt, query Groq or NVIDIA NIM (errors treated like invalid output), validate, transmit.

%-------------------------------------------------------------------
\subsection[Embodiment firmware]{Embodiment firmware (\textit{phase2\_obstacle\_avoidance.ino})}
\label{subsec:firmware}

Responsibility: Run the real-time sense--act loop on the ESP32: trigger/echo ultrasonic measurements with \textit{pulseIn}, map distances through motor primitives (\textit{forward}, pivots, etc.) via TB6612FNG direction pins and LEDC PWM, refresh the SSD1306 via I\textsuperscript{2}C, and exchange newline-terminated messages over \textit{Serial}.

Modes: \textit{AI\_MODE} activates when a valid JSON line arrives (\textit{ArduinoJson} parse); \textit{AUTO\_MODE} executes distance-threshold rules when no JSON is seen for \textit{AI\_TIMEOUT\_MS} (5000\,ms). Constants such as \textit{OBSTACLE\_DIST} and \textit{WALL\_DIST} tune avoidance aggressiveness independently of the LLM policy on the Pi~\cite{brooks1986robust}.

\section{Phase~4 Multimodal Architecture}
\label{sec:phase4_arch}

Phase~4 extends the intelligence layer with voice, vision, and remote interaction capabilities orchestrated by a 7-state event-driven machine.

%-------------------------------------------------------------------
\subsection{7-State Machine}
\label{subsec:statemachine}

\textbf{Figure~\ref{fig:state_machine_ch5}} shows the state-transition graph for the Phase~4 orchestrator. The machine begins in IDLE and transitions through LISTENING, THINKING, ACTING, SEARCHING, SPEAKING, and REPORTING states. A global cancel path (triggered by obstacle detection or an explicit stop command) can abort any active state and return the system to IDLE, ensuring that safety is never blocked by an ongoing task.


\begin{figure}[H]
\centering
\includegraphics[width=1.0\textwidth]{5_7.png}
\caption[7-state event-driven machine for the Phase 4 multimodal agent]{\textbf{7-state event-driven machine for the Phase~4 multimodal agent.}}
\label{fig:state_machine_ch5}
\end{figure}

Four concurrent daemon threads support the state machine: (1)~openWakeWord~\cite{openwakeword2024} detector running offline ONNX inference at 8\% CPU, (2)~ESP32 heartbeat monitor parsing telemetry and propagating obstacle events, (3)~Telegram bot long-polling, and (4)~TTS worker queue draining speech requests.

%-------------------------------------------------------------------
\subsection{ReAct Search Algorithm}
\label{subsec:react_search}

For ``find'' tasks, a specialised ReAct loop~\cite{yao2023react} (\textbf{Fig.~\ref{fig:react_flow}}) combines vision, movement, and semantic memory. Scene descriptions are compared using Ratcliff--Obershelp string similarity~\cite{ratcliff1988} to prevent revisiting previously explored locations.
