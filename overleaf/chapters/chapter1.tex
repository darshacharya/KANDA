\chapter{INTRODUCTION}
\label{ch:intro}

This chapter introduces Knowledge-driven Autonomous Navigation and Decision-making Agent (KANDA), a multimodal embodied robot agent that I built to explore how Large Language Models can control a physical robot safely and reliably on a budget. I started this project with a simple question: how cheaply could I build a robot that listens, sees, reasons, and moves without crashing? What I discovered along the way taught me more about AI safety, hardware constraints, and embodied intelligence than I expected. This chapter covers the context, motivation, technical challenges I faced, what I built to solve them, and how the rest of the report is organized.

%-------------------------------------------------------------------
\section{Overview of KANDA}
\label{sec:overview}

Rule-based robots work until they encounter something the programmer did not anticipate. A wall at an odd angle, two obstacles that create a narrow gap, or a piece of furniture moved since yesterday, any of these can deadlock a threshold-based system because the rules simply have no clause for that configuration. The robot stops, oscillates, or crashes.

Large Language Models (LLMs) offer a way out of this rigidity. Given a text description of the robot's situation (sensor distances, legal actions, speed limits), an LLM can propose contextually sensible commands even in novel layouts~\cite{vaswani2017attention}. The catch is that LLMs have no built-in awareness of hardware. They may suggest actions the robot cannot perform or speeds it cannot survive~\cite{driess2023palme}. Bridging this gap between linguistic reasoning and physical execution is the central challenge of embodied AI, and it is the problem KANDA was designed to solve.

KANDA addresses this opportunity by implementing a complete multimodal embodied robot agent in which an ESP32 microcontroller serves as the physical executor (body) and a Raspberry Pi~4 running the \textit{vision\_module/} intelligence layer serves as the cognitive reasoner (brain). The system operates as a closed-loop sense-reason-validate-act pipeline: ultrasonic sensors and (in Phase~4) a Pi Camera measure the environment; sensor telemetry and optional scene descriptions are assembled into a body-context prompt dispatched to Groq (text reasoning) or NVIDIA NIM (vision); the returned JSON command is validated through a safety layer; and the validated command drives the motors. If cloud inference fails or an obstacle is detected, the system gracefully degrades to firmware-level emergency stops or AUTO\_MODE, ensuring continuous safe operation. \textbf{Figure~\ref{fig:hw_block}} (Chapter~\ref{ch:srs}) shows the hardware interconnection; an assembled prototype photograph may be added to \textit{images/kanda\_robot.jpg} when available for the viva binder.

\subsection{Embodied Intelligence Architecture}
\label{subsec:architecture}

KANDA operates as a three-layer processing architecture:

\textbf{Sensing \& Communication:}
Three HC-SR04 ultrasonic sensors (front, left, right) measure distances to obstacles at each control cycle. The ESP32 reads sensor values, formats front/left/right ranges and the current action label into a single telemetry line, and transmits this data over UART at 115,200 baud to the Raspberry Pi. Voltage dividers on each ECHO pin convert the 5V HC-SR04 output to approximately 2.5V, protecting the 3.3V-tolerant ESP32 GPIO pins.

\textbf{Reasoning \& Decision:}
The Raspberry Pi receives the telemetry and constructs a hardware-description prompt that communicates the robot's physical capabilities, current sensor readings, valid action vocabulary, speed constraints, and safety rules to Groq or NVIDIA NIM as appropriate. The service returns a JSON object specifying the next action and speed. A safety validator then checks the command against a whitelist of valid actions and clamps speed to the permissible range $[0, 255]$. Any invalid command is replaced with a safe stop.

\textbf{Execution \& Feedback:}
The validated JSON command is transmitted back to the ESP32 over serial. The ESP32 parses the command and drives the TB6612FNG dual motor driver accordingly, while simultaneously displaying the current state on an SSD1306 OLED screen. The firmware implements dual-mode operation: AI\_MODE when valid commands arrive from the Pi, and AUTO\_MODE (rule-based obstacle avoidance) when the Pi is silent for longer than a configured timeout.

\subsection{Global Scenario}
\label{subsec:global}

Two trends converged to make KANDA feasible. On the hardware side, microcontrollers like the ESP32 now cost under \$5 and run dual cores at 240\,MHz with built-in Wi-Fi, enough to sample sensors, drive motors, and parse JSON without breaking a sweat. On the AI side, hosted LLM inference through services like Groq and NVIDIA NIM gives a Raspberry Pi access to 70-billion-parameter reasoning at sub-3-second latency with no local GPU~\cite{shi2016edge,bonomi2012fog}.

The IFR reported 500,000 new industrial robot installations in 2023 and 48\% growth in service robotics~\cite{ifr2024report}. At the research frontier, PaLM-E~\cite{driess2023palme}, RT-1~\cite{brohan2022rt1}, and RT-2~\cite{brohan2023rt2} showed that multimodal language models can generate robot actions grounded in sensor context. SayCan~\cite{ahn2022saycan} demonstrated affordance-aware planning on a mobile manipulator. But all of these run on platforms costing upwards of \$100,000 and require substantial demonstration datasets.

KANDA targets the other end of the cost spectrum. I wanted to know whether the same \textit{behaviours} (voice interaction, obstacle navigation, visual object search) could run on parts from an electronics shop, with zero training data, using only API inference. The answer shapes the rest of this report.

\subsection{Societal Relevance}
\label{subsec:societal}

Embodied AI agents with natural language understanding have direct societal applications:

\begin{itemize}[nosep]
  \item \textbf{Assistive robotics:} Indoor companion robots that can understand spoken instructions and navigate home environments safely benefit elderly and mobility-impaired individuals.
  \item \textbf{Education:} A low-cost platform that demonstrates LLM-robot integration provides hands-on learning for robotics, embedded systems, and AI courses.
  \item \textbf{Search and rescue:} Robots that can reason about sensor data and adapt to novel obstacle configurations are valuable in disaster response scenarios.
  \item \textbf{Safety research:} The safety validation layer demonstrates how to constrain AI-generated actions before physical execution, contributing to the broader discourse on safe AI deployment.
\end{itemize}

From an engineering perspective, the project integrates embedded systems programming (ESP32/Arduino), hardware interfacing (ultrasonic sensors, motor drivers, voltage dividers), inter-processor communication (UART/serial), cloud API integration (Groq, NVIDIA NIM), and software safety engineering into a single cohesive system, making it a complete study in applied software and hardware co-design.

\subsection{Problem Area}
\label{subsec:problem_area}

Current approaches to autonomous mobile robot navigation suffer from three interrelated limitations:

\begin{enumerate}[label=\arabic*.]
  \item \textbf{Rigidity of rule-based control:} Traditional obstacle avoidance algorithms use fixed distance thresholds and pre-programmed turning sequences. When the environment presents a configuration not anticipated by the programmer (e.g., a narrow corridor with asymmetric obstacles), the robot either oscillates between conflicting rules or fails to find a viable path. The system cannot \textit{reason} about the spatial arrangement or consider alternative strategies.

  \item \textbf{Disconnect between language models and physical hardware:} General-purpose LLMs possess strong reasoning capabilities but have no inherent knowledge of a specific robot's physical constraints. Asking a language model ``What should the robot do?'' without communicating the robot's sensor state, actuator capabilities, and safety limits produces hallucinated or physically impossible commands~\cite{ahn2022saycan}. Bridging this semantic gap requires a carefully engineered prompt that grounds the model in hardware reality.

  \item \textbf{Absence of safety guarantees:} LLM outputs are probabilistic and can occasionally produce malformed, out-of-vocabulary, or unsafe commands. A system that directly executes raw LLM output on physical hardware risks motor stalls, collisions, overcurrent conditions, or damage to the robot and its environment. A systematic validation layer between the LLM and the actuators is essential but is absent in most prototype systems.
\end{enumerate}

KANDA addresses all three problems through its hardware-aware prompting, structured JSON command interface, and mandatory safety validation layer.

\section{Specific Details of KANDA}
\label{sec:specific}

KANDA is implemented as a dual-processor system with the following key technical characteristics:

\textbf{Hardware platform:}
\begin{itemize}[nosep]
  \item ESP32 DevKit microcontroller (dual-core Tensilica Xtensa, 240\,MHz, Wi-Fi/Bluetooth)
  \item TB6612FNG dual H-bridge motor driver with PWM speed control (1\,kHz, 8-bit resolution)
  \item 3$\times$ HC-SR04 ultrasonic distance sensors with 1\,k$\Omega$ + 1\,k$\Omega$ voltage dividers
  \item SSD1306 OLED display (128$\times$64, I2C at address \textit{0x3C})
  \item 7.4V LiPo battery with BMS and buck converter (5V regulated output to ESP32)
  \item Raspberry Pi (Python runtime, Groq/NVIDIA API clients, safety validator)
\end{itemize}

\textbf{Communication:}
\begin{itemize}[nosep]
  \item UART serial at 115,200 baud between ESP32 and Raspberry Pi
  \item ESP32 transmits telemetry lines matching \textit{F:\textless cm\textgreater{} L:\textless cm\textgreater{} R:\textless cm\textgreater{} -\textgreater{} \textless ACTION\textgreater}
  \item Raspberry Pi transmits one JSON command per line with fields \textit{action} and \textit{speed}
  \item Auto-mode detection: if no valid JSON received within timeout, ESP32 reverts to standalone operation
\end{itemize}

\textbf{AI reasoning:}
\begin{itemize}[nosep]
  \item \textbf{Groq} (\textit{llama-3.3-70b-versatile}) for text reasoning and ASR; \textbf{NVIDIA NIM} (\textit{meta/llama-3.2-11b-vision-instruct}) for vision; keys via \textit{GROQ\_API\_KEY} and \textit{NVIDIA\_API\_KEY}
  \item \textbf{Alignment:} hardware-description prompt aligns model outputs with actuator affordances; low temperature and JSON-only response format constrain decoding; the validator provides runtime alignment by mapping every candidate command to a safe, whitelisted action and bounded speed~\cite{huang2023grounded,ahn2022saycan}
  \item Hardware-description prompt with explicit action vocabulary, speed range, and safety rules
  \item Temperature 0.2 for deterministic JSON output
  \item Maximum 64 output tokens (command is a single JSON object)
  \item 2-second control loop interval
\end{itemize}

\newpage
\textbf{Safety validation:}
\begin{itemize}[nosep]
  \item Action whitelist (fixed vocabulary):
  \begin{itemize}[nosep,leftmargin=1.25em]
    \item \textit{forward}, \textit{backward}, \textit{left}, \textit{right}
    \item \textit{slight\_left}, \textit{slight\_right}, \textit{stop}
  \end{itemize}
  \item Speed clamping to $[0, 255]$
  \item Type checking on all command fields
  \item Fallback on any validation failure to \textit{\{``action'':``stop'',``speed'':0\}}
\end{itemize}

\textbf{Firmware modes:}
\begin{itemize}[nosep]
  \item \textit{AI\_MODE}: Raspberry Pi sends JSON commands; ESP32 executes them
  \item \textit{AUTO\_MODE}: Standalone rule-based obstacle avoidance (Phase~2 behaviour)
  \item Automatic switching: valid JSON reception $\rightarrow$ AI\_MODE; timeout $\rightarrow$ AUTO\_MODE
\end{itemize}

\section{Literature Review}
\label{sec:litreview}

The literature divides into three clusters: systems that ground LLMs in robot hardware, systems that treat prompts as executable specifications, and systems that compose multiple models for multimodal reasoning.

\textbf{Hardware grounding.} The core question, how to prevent an LLM from proposing actions a robot cannot execute, has been attacked from several angles. Ahn et al.~\cite{ahn2022saycan} trained affordance scores from 68k demonstrations so that SayCan could rank actions by both linguistic plausibility and physical feasibility, achieving 74\% better execution success on a mobile manipulator. Driess et al.~\cite{driess2023palme} embedded raw sensor tokens into PaLM-E's 562B-parameter transformer, letting the model ``see'' joint states and images natively. Brohan et al.~\cite{brohan2023rt2} fine-tuned a vision-language model directly into a policy (RT-2) that doubled generalisation to unseen objects. Vemprala et al.~\cite{vemprala2024chatgpt} took the zero-shot route, showing that structured API prompts with clear capability descriptions suffice for ChatGPT to produce viable robot plans without any fine-tuning. KANDA's approach is closest to this last strategy; I achieve grounding through prompt engineering alone, which eliminates training cost entirely.

\textbf{Prompts as specifications.} Liang et al.~\cite{liang2023code} framed prompts as Python APIs and let the LLM write policy code; Singh et al.~\cite{singh2023progprompt} declared functions and world state so the model generates situated programs. Wei et al.~\cite{wei2022cot} showed that ``think step by step'' prefixes unlock multi-step planning. Yao et al.~\cite{yao2023react} alternated reasoning traces with concrete actions in ReAct, observing outcomes before the next step. Huang et al.~\cite{huang2023grounded} proposed modifying token probabilities during generation using grounding scores. KANDA borrows the ReAct loop structure for its visual search and uses post-generation validation rather than logit intervention, a practical choice since cloud APIs do not expose logits.

\textbf{Multimodal composition.} Zeng et al.~\cite{zeng2023socratic} composed vision, language, and audio models through text interfaces without joint training. Huang et al.~\cite{huang2022innermonologue} fed execution results back into the planner for self-correction. Wake et al.~\cite{wake2023gptrobot} decomposed long-horizon tasks into action sequences via ChatGPT. Wu et al.~\cite{wu2023tidybot} personalised household assistance by learning user preferences from a few examples. Hu et al.~\cite{hu2023llmplanner} re-planned dynamically when actions failed. KANDA's Phase~4 realises multimodal composition on commodity hardware: Groq handles text reasoning, NVIDIA NIM handles vision, and openWakeWord handles offline wake detection. These three specialised models are coordinated through the 7-state orchestrator.

\textbf{Hardware reference.} The ESP32 Technical Reference Manual~\cite{espressif2023esp32} documents the LEDC PWM peripheral, UART controllers, GPIO constraints, and I2C bus configuration that directly governed my firmware design choices and pin allocation.

\section{Problem Statement}
\label{sec:problem}

Existing approaches to LLM-driven robot control suffer from three unsolved problems:

\begin{enumerate}[nosep]
  \item \textbf{Rule-based rigidity:} Threshold-based obstacle avoidance cannot reason about novel spatial configurations and deadlocks in cluttered environments.
  \item \textbf{Ungrounded LLM outputs:} Without explicit hardware context, language models hallucinate invalid actions, out-of-range speeds, and malformed responses (observed in 40\% of raw outputs).
  \item \textbf{Timing mismatch:} Cloud inference takes 1.5--4 seconds while physical obstacles appear in under 100\,ms, making pure cloud-dependent control unsafe.
\end{enumerate}

KANDA addresses all three through body-context prompting, a deterministic safety validator, and firmware-level reflexes, on a platform costing less than \$77.

\section{Objectives}
\label{sec:objectives}

\begin{enumerate}[label=\arabic*.]
  \item Design a dual-processor architecture (ESP32 + Raspberry Pi) communicating via JSON over UART.
  \item Develop a hardware-aware context builder that grounds LLM prompts in live sensor state and action constraints.
  \item Implement a safety validation layer that whitelists actions, clamps speed, and substitutes safe fallback on failure.
  \item Build dual-mode firmware with automatic fallback to rule-based avoidance on communication timeout.
  \item Demonstrate the complete sense-reason-validate-act loop on commodity hardware (total cost below \$77).
  \item Evaluate through voice commands, visual search, fault injection, and ablation experiments.
\end{enumerate}

\section{Summary}
\label{sec:ch1summary}

This chapter presented the motivation, context, and design philosophy of KANDA, a multimodal embodied robot agent powered by LLMs with hardware-aware action generation. The key insight driving the project is that language models can serve as the reasoning brain of a physical robot provided they are explicitly grounded in the robot's hardware capabilities through structured prompts, and their outputs are validated through a safety layer before reaching the actuators. KANDA implements this insight as a dual-processor architecture where an ESP32 handles real-time sensing and motor execution while a Raspberry Pi running Groq and NVIDIA NIM provides contextual reasoning at each control cycle. The problem statement articulates the limitations of rule-based control, the hardware-grounding gap in LLM-robot integration, and the absence of safety guarantees in existing prototype systems. The six project objectives span the dual-processor architecture, hardware-aware prompting, safety validation, dual-mode firmware, commodity hardware demonstration, and scenario-based evaluation. The chapter concluded with the scope boundaries, phased methodology, and the organization of the report through implementation, testing, results, and conclusion (Chapters~6--9).
