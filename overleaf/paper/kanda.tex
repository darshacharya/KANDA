\begin{abstract}
\textbf{KANDA} is a low-budget multimodal embodied agent built for under~\$77 using ESP32, Raspberry Pi~4, and a camera module.
It supports named-object search, indoor navigation, and both speech and keyboard input.
\groq{} handles language reasoning while \nvidia{} provides visual understanding.
A three-layered control architecture based on Brooks' subsumption model is employed: (i)~a body-context prompt grounding the LLM in live sensor data and action limits, (ii)~a deterministic critic on the Pi mapping LLM output to legal commands or \safe{}, and (iii)~a firmware reflex on the ESP32 halting motion when ultrasonic range falls below 15\,cm, independent of cloud latency.
Ablation over 10 trials per condition shows that removing scene context leads to 15\% unsafe plans, absence of episodic memory causes 60\% redundant search steps, and disabling the firmware stop results in 30\% near-miss events.
On 60 voice utterances, macro-averaged intent F1 is 0.94, visual search succeeds in 8 of 10 trials, and all eight injected faults terminate safely.
\end{abstract}

\section{Introduction}
\label{sec:intro}
% ====================================================================

Embodied artificial intelligence has advanced considerably, but the systems demonstrating the most impressive capabilities tend to require hardware and data resources beyond reach of most research groups. PaLM-E~\cite{driess2023palme} employs a 562-billion-parameter model trained on massive multimodal corpora. SayCan~\cite{ahn2022saycan} targets mobile manipulators costing upwards of one hundred thousand dollars and requires tens of thousands of demonstration episodes. RT-1~\cite{brohan2022rt1} and RT-2~\cite{brohan2023rt2} depend on large-scale teleoperation datasets and web-scale fine-tuning that presuppose institutional compute budgets. This paper asks: can comparable behaviours, including voice interaction, indoor navigation, visual object search, and collision avoidance, run on commodity hardware costing under eighty dollars with zero robot-specific training?

\begin{figure}[t]
\centering
\slotfig{0.9\columnwidth}{6.2cm}{kanda_robot}
\caption{KANDA prototype}
\label{fig:proto}
\end{figure}

Building such a system exposes four engineering gaps. First, the absence of body context: when an LLM controls a robot without knowing what movements are physically possible or what sensors currently report, it produces infeasible commands~\cite{ahn2022saycan,vemprala2024chatgpt}. Second, intent ambiguity: ``go forward'' requires a validated motor command, while ``find my bottle'' requires a multi-step visual search loop inspired by Inner Monologue~\cite{huang2022innermonologue} and ReAct~\cite{yao2023react}. Third, model garbage: the language model often produces corrupted outputs, markdown code fences, or hallucinated action names~\cite{huang2023grounded}. Fourth, timing mismatch: a physical obstruction can appear in 100\,ms~\cite{brooks1986robust}, whereas cloud inference takes 1.5 to 4 seconds.

KANDA addresses these gaps through a body-context assembler grounding every model call in live hardware state, an intent router classifying utterances before dispatch, a validator function $V$ mapping any model output to a safe motor command, and firmware reflexes on the ESP32 halting motion independently of the Pi or cloud. The entire system runs on a Raspberry Pi~4 paired with an ESP32, communicating over a 115{,}200-baud UART link, with cloud inference handled by free-tier API calls to Groq and NVIDIA NIM. No model fine-tuning, reinforcement learning, or demonstration data collection is required at any stage.

This paper makes six contributions: (1)~a fully functional multimodal embodied agent built for under \$77 supporting voice, vision, text, and Telegram interaction; (2)~a body-context grounding scheme with a shared action vocabulary consistent across prompt, validator, and firmware; (3)~an intent classification mechanism paired with episodic visual search; (4)~ablation evidence for a deliberative--critic--reflex safety architecture; (5)~a seven-state machine design preserving fast obstacle handling despite slow cloud calls; (6)~demonstration modes suitable for classroom and exhibition deployment.

\section{Related Work}
\label{sec:related}
% ====================================================================

The problem of grounding language models in physical robot capabilities has been approached from several directions. SayCan~\cite{ahn2022saycan} learns affordance functions from thousands of demonstrations to score which actions are physically feasible. KANDA takes a different approach by embedding affordances directly in the prompt at zero training cost, making the model aware of valid actions, speed limits, and current sensor measurements. Chain-of-thought prompting~\cite{wei2022cot} improves model executability, and Huang et al.~\cite{huang2022zeroshot} showed that language models serve as zero-shot planners when prompted properly. The body-context method I propose builds on this insight by incorporating telemetry at every inference step.

Several systems compose LLM output into executable control programs. Socratic Models~\cite{zeng2023socratic} chain multiple foundation models, Code as Policies~\cite{liang2023code} generates Python control code, and ProgPrompt~\cite{singh2023progprompt} frames tasks as program synthesis. These produce complex outputs difficult to validate at runtime. KANDA restricts the interface to single-line JSON commands validated before UART transmission. Inner Monologue~\cite{huang2022innermonologue} and ReAct~\cite{yao2023react} interleave observations with model decisions in a closed loop. The visual search in KANDA draws on this principle but uses VLM scene descriptions with episodic deduplication memory to prevent revisiting explored locations.

On safety, Amodei et al.~\cite{amodei2016safety} argued that structural safeguards are necessary beyond scaling model capabilities. Brooks~\cite{brooks1986robust} established the subsumption architecture where fast reactive layers override slower deliberative layers. The Dynamic Window Approach~\cite{fox1997dwa} informs the ultrasonic threshold design. Edge computing surveys~\cite{bonomi2012fog,shi2016edge} motivate placing safety-critical logic on the microcontroller. KANDA makes the critic layer explicit and deterministic, paired with a hardware reflex that cannot be circumvented through prompt engineering or hallucination.

\section{Formal Problem Definition}
\label{sec:formal}
% ====================================================================

Before describing the system architecture, I define the constraints that any valid command must satisfy. The robot's action vocabulary consists of seven motor primitives: $\mathcal{A} = \{\text{forward}, \text{backward}, \text{left}, \text{right}, \text{slight\_left}, \text{slight\_right}, \text{stop}\}$. Each command pairs one of these actions with an integer speed value drawn from the range $[0, 255]$, which corresponds to the PWM duty cycle applied to the motor driver.

\textbf{Definition 1 (Safe command).}
A command $c = (a, s)$ where $a$ denotes the action and $s$ denotes the speed is safe if and only if:
\begin{equation}
\label{eq:safety}
a \in \mathcal{A} \;\wedge\; s \in \mathbb{Z} \;\wedge\; 0 \leq s \leq 255
\end{equation}

\textbf{Definition 2 (Critic / validator).}
The validator is a total function $V:\text{Any} \to \mathcal{A} \times [0,255]$ satisfying:
\begin{equation}
\label{eq:validator}
\forall\, x \in \text{Any}:\; V(x) \text{ is safe per Eq.~\eqref{eq:safety}} \;\wedge\; V(x) \text{ terminates}
\end{equation}
In practice, any unrecognised action maps to \safe{}, any non-integer speed maps to \safe{}, and out-of-range numeric speeds are clamped to $[0, 255]$ before transmission.

\textbf{Definition 3 (Timing constraint).}
The firmware reflex latency $t_r$ must satisfy $t_r \ll t_c$ where $t_c$ is the cloud round-trip time:
\begin{equation}
\label{eq:timing}
t_r \approx 47\,\text{ms (mean)}, \quad
t_c \in [1500, 4000]\,\text{ms}, \quad
\frac{t_c}{t_r} \approx 40
\end{equation}
The ESP32 firmware runs a cooperative loop at approximately 10\,Hz. Within each 100\,ms iteration, the reflex logic reads all three ultrasonic sensors and evaluates the stopping condition without waiting for any Pi or cloud response. This separation ensures that network failures or API timeouts cannot delay the safety-critical path.

\section{System Design}
\label{sec:arch}
% ====================================================================

\subsection{Three Tiers}

The system is organised into three processing tiers, illustrated in Fig.~\ref{fig:arch}. Each tier is designed to reach a safe state independently if the tiers above it fail or become unreachable. This fail-safe independence is the central architectural principle: power loss at any higher tier must never leave a lower tier in an unsafe motion state.

\begin{figure}[t]
\centering
\slotfig{0.9\columnwidth}{5.5cm}{architecture}
\caption{Three-tier layout: cloud deliberation, edge critic and state machine, device reflex and sensing.}
\label{fig:arch}
\end{figure}

The \textbf{cloud tier} handles all language and vision reasoning via Groq for text and NVIDIA NIM for vision, with temperature set to 0.1 for classification tasks. It performs scene analysis, intent classification, and JSON action generation. Latency ranges from 1.5 to 4 seconds, and all outputs are treated as untrusted until validated by the critic.

The \textbf{edge tier} runs on the Raspberry Pi~4 and hosts the Python-based vision module. It contains the state machine, the body-context builder, the plan executor, the openWakeWord~\cite{openwakeword2024} wake phrase detector trained on \emph{Hey Kanda}, the gTTS speech synthesis output, and the Telegram message polling loop.

The \textbf{device tier} runs on the ESP32 microcontroller. It samples three HC-SR04 ultrasonic sensors on each iteration of its main loop, parses one incoming JSON command per line from the UART, and applies an emergency stop whenever the robot is moving forward and the front sensor reports a range below 15\,cm.

These three tiers map onto a deliberative--critic--reflex decomposition mirroring Brooks' subsumption architecture~\cite{brooks1986robust}: the cloud proposes actions conditioned on body context; the edge validator $V$ rejects or clamps every command before transmission (Listing~\ref{lst:validator}); the device halts motors and reports \texttt{OBSTACLE} independently of cloud latency. A heartbeat thread on the Pi (100\,ms interval) forwards obstacle events to ensure non-blocking THINKING and SEARCHING states.

\subsection{Wire Communication Protocol}

The Pi and ESP32 communicate via UART at 115{,}200 baud using a text-based protocol. The Pi sends single JSON objects per line (e.g., {\scriptsize\texttt{\{"action":"forward","speed":120,"state":"searching"\}}}). The ESP32 responds with telemetry strings (e.g., {\scriptsize\texttt{F:30.5 L:21.0 R:16.4 -> FORWARD}}). The \texttt{state} field in downlink messages allows the ESP32 to adjust its LED display and buzzer feedback based on the current system mode. This plain-text approach allows debugging with any serial monitor and avoids binary framing complexity that would complicate fault diagnosis during development.

\section{Mechanisms}

\subsection{Body-Context Assembler}
\label{sec:bodyctx}

Before each model inference call, the body-context assembler produces a textual block containing the latest VLM scene description, movement capabilities, speed constraints, current sensor data with proximity alarms, and recent action history. Listing~\ref{lst:bodyctx} shows an example. The block is regenerated from scratch on every call rather than cached, ensuring the model always reasons over the most recent sensor state. Including the last three executed actions prevents the model from issuing redundant repeated commands when the robot has already reached the desired heading or position.

\begin{lstlisting}[caption={Body-context block (rebuilt each inference call)},
  label={lst:bodyctx}, float=tp]
You are a robot with two wheels called KANDA.
Capabilities include forward, reverse, left, right,
  slight left, slight right, and stop.
  Speed range: from 0 to 255. Camera resolution: 640x480.
Restrictions: only approximate turns, no stairs or arm.
Sensors:
  Left sensor = 18.4 cm  WARNING: imminent collision
  Right sensor = 62.0 cm
  Left sensor = 25.3 cm
Scene: "A desk with laptop and water bottle."
Final actions: ["forward," "forward," "slight_left"]
State: Searching.
"I need to find my water bottle." User stated.
JSON ONLY in your answer please.
\end{lstlisting}

\subsection{Task Agent and Episodic Visual Search}
\label{sec:search}

Each utterance is classified into one of four classes: \texttt{COMMAND} for motion, \texttt{QUESTION} for scene queries, \texttt{TASK} for complex goals like finding an object, and \texttt{UNKNOWN} for unrecognised inputs. For \texttt{TASK} utterances, the algorithm generates a JSON list of up to 50 steps including actions such as move, talk, \texttt{capture\_check}, \texttt{loop\_while}, and wait.

The search routine (Algorithm~\ref{alg:search}) repeatedly captures images, obtains VLM descriptions, filters for the target using Ratcliff--Obershelp similarity~\cite{ratcliff1988} with episodic memory (threshold $\tau{=}0.7$, reduced to 0.5 after five revisits), and selects movement based on ultrasonic geometry. This approach extends the ReAct~\cite{yao2023react} paradigm with episodic deduplication.

\begin{algorithm}[t]
\caption{Episodic visual search (VLM-driven)}
\label{alg:search}
\begin{algorithmic}[1]
\REQUIRE target $T$, max steps $N{=}20$
\STATE $\mathcal{M} \leftarrow \emptyset$; $\tau \leftarrow 0.7$; $\mathit{skip} \leftarrow 0$
\FOR{$i = 1$ \TO $N$}
  \STATE $f \leftarrow \text{capture()}$;
         $s \leftarrow \text{VLM.describe}(f)$
  \IF{$\exists\, m \in \mathcal{M}: \text{sim}(s, m) > \tau$}
    \STATE $\mathit{skip} \leftarrow \mathit{skip} + 1$
    \IF{$\mathit{skip} > 5$}
      \STATE $\tau \leftarrow 0.5$
    \ENDIF
    \STATE \textbf{continue}
  \ENDIF
  \STATE $\mathcal{M} \leftarrow \mathcal{M} \cup \{s\}$; $\mathit{skip} \leftarrow 0$
  \IF{$\text{VLM.check}(f, T) = \textsc{yes}$}
    \RETURN \textsc{found}, $s$
  \ENDIF
  \STATE execute(heuristic\_move(sensors)); sleep
\ENDFOR
\RETURN \textsc{not\_found}
\end{algorithmic}
\end{algorithm}

\subsection{Safety Validator (Critic)}
\label{sec:validator}

The safety validator is the deterministic critic layer between language model output and UART transmission. It enforces four invariants on every command:

\begin{align}
\text{I}_1&: \; r \text{ is a dict with keys } \texttt{action},\, \texttt{speed} \label{inv:dict}\\
\text{I}_2&: \; r[\texttt{action}] \in \mathcal{A} \quad(\text{else } \to \safe{}) \label{inv:action}\\
\text{I}_3&: \; r[\texttt{speed}] \in \mathbb{Z} \quad(\text{else } \to \safe{}) \label{inv:int}\\
\text{I}_4&: \; r[\texttt{speed}] = \text{clamp}(r[\texttt{speed}],\, 0,\, 255) \label{inv:range}
\end{align}

\begin{lstlisting}[language=Python, caption={Critic $V$: total, safe output (matches \texttt{safety\_validator.py})},
  label={lst:validator}, float=tp]
SAFE = {"action": "stop", "speed": 0}
def validate(cmd):
    if not isinstance(cmd, dict):  return SAFE
    action = cmd.get("action")
    speed  = cmd.get("speed", 100)
    if action not in VALID_ACTIONS: return SAFE
    try:    speed = int(speed)
    except: return SAFE
    speed = max(0, min(255, speed))
    return {"action": action, "speed": speed}
\end{lstlisting}

\subsection{Firmware Reflex and Pi Cancel}
\label{sec:reflex}

On each ESP32 loop iteration, the firmware checks whether the robot is moving forward. If the front ultrasonic sensor reports distance $d_F < 15$\,cm, it immediately zeros motor output, transitions to \texttt{obstacle} state, and includes \texttt{OBSTACLE} in telemetry. Mean latency from detection to halt is $47 \pm 21$\,ms (Table~\ref{tab:timing}), dominated by the 100\,ms loop period rather than cloud round-trip time. On the Pi, a heartbeat thread at 100\,ms intervals reads telemetry, updates body-context structures, and sets a global cancel flag causing any THINKING or SEARCHING state to exit without waiting for its cloud call.

\subsection{Seven-State Machine}
\label{sec:fsm}

The Pi implements a seven-state machine: \texttt{IDLE}, \texttt{LISTENING}, \texttt{THINKING}, \texttt{ACTING}, \texttt{SEARCHING}, \texttt{SPEAKING}, and \texttt{REPORTING} (Fig.~\ref{fig:statemachine}). Four concurrent threads handle wake word detection, ESP32 telemetry, Telegram polling, and TTS output. No cloud call or search step blocks the reflex handling path; the cancel mechanism is event-driven from inbound telemetry, propagating obstacle detection within one heartbeat period.

\subsection{Experimental Protocol}
\label{sec:protocol}

All experiments ran in a $3\times 4$\,m indoor lab (desks, chairs, bookshelf; ambient noise $<$40\,dB; local Wi-Fi) using \groq{} for text, \nvidia{} for vision, firmware \texttt{firmware\_phase4.ino}, and Python~3.10+ on Pi OS. Metrics: \emph{Action correct} (motion consistent with request), \emph{Intent correct} (label matches program categories), \emph{Failure} (dangerous motion, parse error, timeout), \emph{Near-miss} (object within 15\,cm during forward motion). Six paraphrase types with ten trials each ($n{=}60$) for voice. Visual search: ten trials from five item categories, target found in $<$20 motions. Ablation: one layer blocked per condition ($n{=}10$; Table~\ref{tab:ablation}). Baselines: ESP32 \texttt{AUTO\_MODE} (rule-based avoidance, no voice) and prompt-only (validator bypassed, offline playback of 50 outputs). Hardware cost in Table~\ref{tab:bom}.

\subsection{Visual Object Search}

The robot located target items in 8 of 10 attempts, averaging seven search steps per success. The two failures occurred when furniture fully occluded the target from all reachable vantage points within the 20-step limit. The adaptive threshold $\tau$ decreased from 0.7 to 0.5 three times when encountering visually similar environments. Items placed at floor level or partially hidden behind chair legs proved more challenging than items on desks or shelves, as the fixed camera height (approximately 25\,cm) limits the effective field of view for ground-level objects. Among the five item categories tested (bottle, book, backpack, mug, phone), the backpack category had the highest first-attempt detection rate due to its distinctive visual features in VLM descriptions.

\subsection{Fault Injection}

Eight deliberate failure scenarios (Table~\ref{tab:faults}) verified safe behaviour under adverse conditions. In every case, the robot stopped within 200\,ms of fault onset with no continued motion toward obstacles. The most revealing scenario was API key revocation during an active search: the validator received a non-JSON error response from the cloud, correctly mapped it to \safe{}, and the robot halted gracefully while speaking an error message. The USB-unplug test confirmed that the ESP32 continues autonomous obstacle avoidance even when the Pi is completely disconnected, validating the independence of the device-tier safety layer.

\section{Discussion}
\label{sec:discussion}
% ====================================================================

The three-layer structure handles failure cases that no single layer could address alone. A validated command may become unsafe if the environment changes between validation and execution; for instance, a ``forward'' command issued when the path is clear becomes dangerous if an obstacle appears mid-execution. The firmware reflex covers this gap, providing continuous protection without re-querying the language model.

The body-context assembler proved essential for grounding the model in physical constraints. Without it, the LLM occasionally generated actions outside the motor vocabulary or requested speeds exceeding the PWM range. Including live sensor readings in the prompt also reduced the frequency of forward commands when ultrasonic values indicated narrow clearance, though this deliberative avoidance operates on a much slower timescale than the firmware reflex.

The episodic deduplication memory addressed a subtle failure mode during visual search. Without it, the robot frequently oscillated between two visually similar locations, consuming all 20 search steps without progressing. The adaptive threshold mechanism ($\tau$ reduced from 0.7 to 0.5 after five skipped frames) balances false positives against the need to escape repetitive loops.

The ablation results (Table~\ref{tab:ablation}) confirm that deliberation and reflex address fundamentally different failure classes on different timescales. Removing deliberative grounding reintroduces planning errors; removing the reflex reintroduces physical safety violations. Neither layer is redundant. The 42\% structural failure rate in raw model outputs underscores why a permissive pass-through approach to LLM-generated robot commands is unsafe regardless of prompt quality.

\subsection{Limitations and Future Work}

Three ultrasonic sensors leave angular blind spots between the 30-degree cones, meaning objects approaching from the side at shallow angles may not trigger the reflex until dangerously close. There is no manipulation or SLAM capability, so the robot cannot open doors or build persistent maps across sessions. All evaluation was conducted in a single room with small samples ($n{=}10$ per condition), limiting statistical power and generalisability to other environments. Cloud dependency introduces both latency variability and ongoing API cost; a single extended session of 50 inference calls costs approximately \$0.02 at current Groq pricing but remains unavailable without internet connectivity.

Future work targets an on-device Gemma-class model running quantised inference on the Pi to eliminate cloud dependency entirely. A depth camera would replace the ultrasonic sensors for denser 2D obstacle mapping. Wheel odometry combined with visual place recognition would enable metric mapping and multi-room navigation. Finally, a larger evaluation campaign across diverse indoor environments with hardware-in-the-loop logged benchmarks would strengthen the statistical evidence for each architectural claim.

% ====================================================================
\section{Conclusion}
\label{sec:conclusion}
% ====================================================================

This paper presented KANDA, a multimodal embodied robot agent demonstrating how explicit safety architecture makes cloud-based LLM reasoning viable for physical robot control on hardware costing under eighty dollars. The deliberative--critic--reflex decomposition provides safety at three timescales: the prompt grounds the model in physical reality before inference, the validator ensures correctness before transmission, and the firmware reflex provides millisecond-scale obstacle protection regardless of network conditions.

On the evaluation suite, the system achieves a macro-averaged intent F1 of 0.94 across 60 voice utterances, successfully locates target objects in 8 of 10 visual search trials, and terminates safely under all eight injected fault scenarios. The ablation study confirms that prompt grounding, episodic search memory, syntactic validation, and the firmware reflex each address non-overlapping failure classes, making all four components necessary. These results suggest that the barrier to building safe, multimodal embodied agents is primarily architectural rather than computational, and that careful layering of deterministic safety mechanisms around probabilistic language models can yield reliable physical behaviour even on inexpensive hardware.
